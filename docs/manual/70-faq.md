# FAQ 및 트러블슈팅

## 같은 메시지가 두 번 처리돼요

정상이며 설계된 동작이다. filequeue는 **at-least-once**라 장애 복구 시 같은 메시지를 다시 전달할
수 있다(예: 소비자가 ACK 직전에 죽으면 다음 리더가 재처리). 해결책은 **소비자를 멱등하게**
만드는 것이다.

- 메시지에 고유 ID를 넣고, 처리 완료한 ID를 기록해 두었다가 중복을 건너뛴다.
- "잔액에 +10" 대신 "잔액을 X로 설정"처럼 여러 번 적용해도 결과가 같은 연산으로 설계한다.
- 외부 시스템에 쓸 때는 그 시스템의 멱등 키/트랜잭션을 활용한다.

중복을 원천 차단(exactly-once)하려면 소비 측에 ID 기반 dedup 원장이 추가로 필요하다. 현재
filequeue는 at-least-once까지를 보장한다.

## 새 공유 스토리지를 도입할 때

filequeue는 두 가지 파일시스템 원자성에 의존한다 — 같은 볼륨 내 `rename`의 원자성, 배타
생성(`O_EXCL`/`CREATE_NEW`)의 원자성. 교체형 rename이 동시에 읽는 쪽에 원자적이지 않은 FS(교체 순간
ENOENT가 잠깐 보임, Cygwin/NTFS 실측)도 있는데, 라이브러리가 짧은 재시도로 흡수하며 `test_atomicity`
[6]이 그 재시도로 충분한지 검사한다. 새 스토리지(특히 NFS/SMB/클러스터 FS)에서는 이 전제가
성립하는지 **먼저 검증**하라.

```bash
# 대상 스토리지의 경로를 인자로 주어 원자성 하니스 실행
./build/test_atomicity /mnt/shared/_atom_check
```

모든 검사가 PASS여야 한다. 실패하면 그 스토리지에서는 큐의 정확성이 보장되지 않는다.

## 노드 간 시계가 안 맞아요

문제되지 않는다. filequeue는 리스 만료를 각 노드의 로컬 시계가 아니라 **공유 FS의 시각**으로
판단한다(임시 파일 mtime을 읽음). 모든 노드가 같은 시계를 보므로 wall-clock skew와 무관하다.
NTP 동기화가 안 된 환경에서도 동작한다.

## 아무도 메시지를 소비하지 않아요

활성 리더가 없을 가능성이 높다. 점검 순서:

1. 소비자 프로세스가 떠 있고 `fq_acquire_leadership`을 시도하는가?
2. `control/leader.info`의 만료시각이 과거인가(리더 부재) 미래인가(리더 존재)?
3. 활성 리더가 있다면 `fq_renew_lease`를 주기적으로 부르고 있는가? 안 부르면 리스 만료 후
   인수/중복이 반복된다. (`fq_consume`을 쓰면 자동이다. 메시지 하나가 리스보다 오래 걸리면
   `fq_heartbeat`를 호출하라.)
4. `fq_open`이 `FQ_EINVAL`(-7)로 실패하고 있지 않은가? `node_id`에 공백·`/`·`__` 등이 들어 있으면
   큐가 열리지 않는다([식별자 규칙](#식별자-규칙)).

## inflight에 파일이 계속 남아 있어요

파일명의 `__t<token>`을 `control/leader.info`의 현재 token과 비교하라.

- **옛 token**(현재보다 작음): 죽은 선임자나 좀비가 남긴 것이다. 활성 리더가 **다음 하트비트에
  `fq_recover_stale`로 자동 회수**한다. 회수가 안 된다면 활성 리더가 있는지, 저수준 API를 쓰는
  소비자라면 하트비트 때 `fq_recover_stale`를 부르는지 확인하라.
- **현재 token**: 지금 리더가 처리 중이다. 오래 남아 있다면 그 리더의 처리 로직이 멈춘 것이다.
  리더 프로세스가 죽으면 리스 만료 → 인수 → 회수로 재처리된다.

## 메시지 순서가 보장되나요

엄밀한 전역 FIFO는 보장하지 않는다. 단일 활성 소비자가 파일명(시각+seq) 정렬 순으로
처리하므로 **best-effort FIFO**다. 장애 복구 시 재처리로 인한 미세한 재정렬은 발생할 수 있다.
엄격한 순서가 필요하면 `stream_key`로 파티셔닝해 파티션 내 순서만 보장하는 방식을 쓴다.

## Windows에서 빌드하려면

Cygwin 환경에서는 POSIX 경로(`fq_fs_posix.c`)로 그대로 빌드된다. 네이티브 Windows(MSVC)에서는
`fq_fs_win32.c`가 선택된다. 단, win32 구현은 개발 환경(Cygwin)에서 컴파일되지 않아 MSVC에서 별도
검증이 필요하다. 도입 전 MSVC로 빌드해 `ctest`와 `test_atomicity`를 대상 스토리지에서 확인하라.

## `FQ_EINVAL`(-7)이 나와요

`node_id` 또는 `stream_key`가 [식별자 규칙](#식별자-규칙)을 어겼다. 영문자·숫자·`.`·`-`·`_`만
쓰고, 밑줄을 두 번 연속(`__`) 쓰지 말라. 호스트명을 그대로 쓰는 경우 FQDN의 `.`은 괜찮지만 공백이나
비ASCII 문자는 안 된다.
