# FAQ 및 트러블슈팅

## 같은 메시지가 두 번 처리돼요

정상이며 설계된 동작이다. filequeue는 **at-least-once**라 장애 복구 시 같은 메시지를 다시 전달할
수 있다(예: 소비자가 ACK 직전에 죽으면 다음 리더가 재처리). 해결책은 **소비자를 멱등하게**
만드는 것이다.

- 메시지에 고유 ID를 넣고, 처리 완료한 ID를 기록해 두었다가 중복을 건너뛴다.
- "잔액에 +10" 대신 "잔액을 X로 설정"처럼 여러 번 적용해도 결과가 같은 연산으로 설계한다.
- 외부 시스템에 쓸 때는 그 시스템의 멱등 키/트랜잭션을 활용한다.

중복을 원천 차단(exactly-once)하려면 소비 측에 ID 기반 dedup 원장이 추가로 필요하다. 현재
filequeue는 at-least-once까지를 보장한다.

## 새 공유 스토리지를 도입할 때

filequeue는 두 가지 파일시스템 원자성에 의존한다 — 같은 볼륨 내 `rename`의 원자성, 배타
생성(`O_EXCL`/`CREATE_NEW`)의 원자성. 교체형 rename이 동시에 읽는 쪽에 원자적이지 않은 FS(교체 순간
ENOENT가 잠깐 보임, Cygwin/NTFS 실측)도 있는데, 라이브러리가 짧은 재시도로 흡수하며 `test_atomicity`
[6]이 그 재시도로 충분한지 검사한다. 새 스토리지(특히 NFS/SMB/클러스터 FS)에서는 이 전제가
성립하는지 **먼저 검증**하라.

```bash
# 대상 스토리지의 경로를 인자로 주어 원자성 하니스 실행
./build/test_atomicity /mnt/shared/_atom_check
```

모든 검사가 PASS여야 한다. 실패하면 그 스토리지에서는 큐의 정확성이 보장되지 않는다.

**SMB(Windows 공유 폴더)라면:** 네이티브 Windows 빌드를 쓰라. Cygwin 빌드는 SMB 위에서 `leader.info`
교체가 깨져(삭제 대기 상태에 걸리거나 사라짐) 리더가 하트비트를 못 하고 대기 노드가 리더십을 빼앗는 것이
관측됐다(`DESIGN.md` §0). `test_atomicity`만으로는 이 문제가 항상 드러나지 않으므로, 리더와 대기 노드를 두
머신에 띄운 `test_election`도 확인하라.

### 두 머신 검증 절차

한 머신 안의 테스트(loopback 포함)로는 클라이언트 캐시처럼 머신 사이에서만 생기는 지연이 드러나지 않는다.
실제 배치와 같은 두 머신(M1, M2)에서, 같은 공유 경로를 각자의 표기로 준다(예: `\\nas\q\check`).
매번 새 디렉터리를 쓸 것.

1. **원자성** — 각 머신에서 한 번씩: `test_atomicity <공유경로>\atom-M1` / `...\atom-M2`. 모두 PASS.
2. **선출 경합** — M1에서 먼저 `test_election <공유경로>\elect A 60000`, 몇 초 안에 M2에서
   `test_election <공유경로>\elect B 55000`. A가 먼저 리더여야 한다(B가 먼저 뜨면 A가 `acquire 실패`로
   끝난다 → 새 디렉터리로 다시). 기대: A `lost=0`·`max_gap` < 1000ms, B `stolen=0`. 둘 다 종료코드 0.
3. **failover** — M1에서 `fq_producer <공유경로>\fo 1000`. 이어서 M1과 M2에서 동시에
   `fq_consumer <공유경로>\fo M1 m1.log 60000` / `... M2 m2.log 60000`. 활성 쪽 프로세스를 강제 종료하면
   다른 쪽이 리스(기본 15초) 뒤 인수해야 한다. 끝난 뒤 두 로그를 합친 고유 줄 수 = 1000,
   `inflight/`는 비어 있어야 한다(중복은 허용).

2와 3은 리더 쪽 머신을 바꿔 한 번 더 한다(캐시 지연은 방향에 따라 다를 수 있다).

## 노드 간 시계가 안 맞아요

문제되지 않는다. filequeue는 리스 만료를 각 노드의 로컬 시계가 아니라 **공유 FS의 시각**으로
판단한다(임시 파일 mtime을 읽음). 모든 노드가 같은 시계를 보므로 wall-clock skew와 무관하다.
NTP 동기화가 안 된 환경에서도 동작한다.

## 아무도 메시지를 소비하지 않아요

활성 리더가 없을 가능성이 높다. 점검 순서:

1. 소비자 프로세스가 떠 있고 `fq_acquire_leadership`을 시도하는가?
2. `control/leader.info`의 만료시각이 과거인가(리더 부재) 미래인가(리더 존재)?
3. 활성 리더가 있다면 `fq_renew_lease`를 주기적으로 부르고 있는가? 안 부르면 리스 만료 후
   인수/중복이 반복된다. (`fq_consume`을 쓰면 자동이다. 메시지 하나가 리스보다 오래 걸리면
   `fq_heartbeat`를 호출하라.)
4. `fq_open`이 `FQ_EINVAL`(-7)로 실패하고 있지 않은가? `node_id`에 공백·`/`·`__` 등이 들어 있으면
   큐가 열리지 않는다([식별자 규칙](#식별자-규칙)).

## inflight에 파일이 계속 남아 있어요

파일명의 `__t<token>`을 `control/leader.info`의 현재 token과 비교하라.

- **옛 token**(현재보다 작음): 죽은 선임자나 좀비가 남긴 것이다. 활성 리더가 **다음 하트비트에
  `fq_recover_stale`로 자동 회수**한다. 회수가 안 된다면 활성 리더가 있는지, 저수준 API를 쓰는
  소비자라면 하트비트 때 `fq_recover_stale`를 부르는지 확인하라.
- **현재 token**: 지금 리더가 처리 중이다. 오래 남아 있다면 그 리더의 처리 로직이 멈춘 것이다.
  (리더가 들고 있지 않은 것 — ack·nack 실패, ack 없이 해제 — 은 고아로 보고 다음 하트비트에 회수한다.)
  리더 프로세스가 죽으면 리스 만료 → 인수 → 회수로 재처리된다.

## 메시지 순서가 보장되나요

엄밀한 전역 FIFO는 보장하지 않는다. 단일 활성 소비자가 파일명(시각+seq) 정렬 순으로
처리하므로 **best-effort FIFO**다. 장애 복구 시 재처리로 인한 미세한 재정렬은 발생할 수 있다.
`stream_key`는 이름에 들어가는 꼬리표일 뿐, 라이브러리가 키별 순서를 따로 보장하거나 분배하지 않는다.
키별 순서는 곧 위의 전역 best-effort 순서다. 특정 메시지를 먼저 처리해야 하면 `fq_publish_ex`의
`FQ_ORDER_HEAD`(맨 앞) / `FQ_ORDER_BEFORE`(지정 메시지 바로 앞)를 쓴다([API > 순서 지정 발행](#순서-지정-발행)).

## Windows에서 빌드하려면

Cygwin 환경에서는 POSIX 경로(`fq_fs_posix.c`)로 그대로 빌드된다. 네이티브 Windows(MSVC)에서는
`fq_fs_win32.c`가 선택된다. win32 구현은 MinGW 네이티브 빌드로 단위·동시성·failover 테스트를 통과했지만
MSVC로는 아직 빌드해 보지 않았다. 도입 전 대상 컴파일러로 빌드해 `ctest`와 `test_atomicity`를 대상
스토리지에서 확인하라.

## `FQ_EINVAL`(-7)이 나와요

다음 중 하나다.

- `node_id` 또는 `stream_key`가 [식별자 규칙](#식별자-규칙)을 어겼다. 영문자·숫자·`.`·`-`·`_`만
  쓰고, 밑줄을 두 번 연속(`__`) 쓰지 말라. 호스트명을 그대로 쓰는 경우 FQDN의 `.`은 괜찮지만 공백이나
  비ASCII 문자는 안 된다.
- 메시지 이름이 너무 길다: `node_id` + `stream_key`가 160자를 넘거나, 네이티브 Win32에서 루트가 길어 claim
  접미사까지 붙인 전체 경로가 260자를 넘는다. `fq_open`이 `FQ_EINVAL`이면 루트가 이 노드의 가장 짧은 메시지도
  둘 수 없을 만큼 길다(Win32) — 루트를 짧게 하라.
- 순서 지정 인자(`mode`가 알 수 없는 값, BEFORE에 고르기 함수 없음, 거듭 끼워 이름이 220자 초과).
- DLQ 함수에 경로 구분자·`.`·`..`가 든 이름, 또는 `fq_redrive`로 되돌려도 claim할 수 없는 긴 이름.
