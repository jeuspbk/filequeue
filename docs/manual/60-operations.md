# 운영 및 튜닝

## 환경변수

| 변수 | 적용 대상 | 의미 |
|---|---|---|
| `FQ_NODE_ID` | `fq_open` | 노드 식별자. `fq_open`의 `node_id` 인자가 `NULL`일 때만 사용되며, 그것도 없으면 `<호스트명>-<pid>`. 메시지 파일명과 리더십 id에 쓰인다. [식별자 규칙](#식별자-규칙)을 따라야 한다(어기면 `FQ_EINVAL`). |
| `FQ_LEASE_MS_OVERRIDE` | 리더 선출/하트비트/리스 자체 만료 감지 | 리스 유효시간(ms)을 런타임에 덮어쓴다. **주로 테스트에서** failover를 빠르게 검증할 때 사용. |

```bash
# 리스를 1.5초로 줄여 failover를 빠르게 관찰
FQ_LEASE_MS_OVERRIDE=1500 ./build/fq_consumer /shared/q nodeA out.log 60000
```

> 운영에서 리스를 너무 짧게 잡으면 일시적 지연(GC, I/O 스파이크)에도 리더십이 흔들려 불필요한
> 인수와 중복 처리가 늘어난다. 하트비트 주기보다 충분히(3~5배) 길게 유지하라.

## 컴파일 타임 노브

리스/재시도 정책은 `include/fq.h`의 `#define`으로 조정한다([API 레퍼런스](#튜닝-노브-컴파일-타임-define) 참고).
값을 바꾼 뒤에는 재빌드해야 한다.

- **`FQ_LEASE_MS` / `FQ_HEARTBEAT_MS`**: 하트비트는 리스의 1/3~1/5로 둔다(`fq_consume`은 리스/3으로 자동,
  `FQ_HEARTBEAT_MS`는 저수준 API용 권장값). 그래야 한두 번의
  하트비트 실패가 곧바로 리스 만료로 이어지지 않는다.
- **`FQ_MAX_ATTEMPTS`**: 같은 메시지가 이 횟수만큼 재처리(재큐잉)되면 `dead/`로 격리된다.
  poison 메시지가 큐를 무한히 막는 것을 방지한다.

## 시각 기준 (clock skew 회피)

리스 만료 판단은 **공유 FS의 시각**을 단일 출처로 사용한다. 내부적으로 `control/`에 임시 파일을
만들어 그 mtime을 읽는다(`fq_fs_now_ms`). 모든 노드가 같은 FS의 시계를 보므로 노드 간 wall-clock
차이(skew)에 영향받지 않는다. 운영 시 노드들의 로컬 시계를 굳이 동기화하지 않아도 된다.

FS 시각 측정은 공유 스토리지에 파일을 만들고 지우는 비용이 있으므로, 잦은 경로(대기 노드 폴링,
메시지 파일명 시각)는 프로세스마다 `FS 시각 - 로컬 시계` 오프셋을 30초마다 한 번 재서 추정한다.
리스 인수·갱신처럼 정확해야 하는 판정만 매번 실제 FS 시각을 잰다. 따라서 대기 노드가 많아도
리더가 살아 있는 동안에는 공유 스토리지에 메타데이터 쓰기가 거의 생기지 않는다.

> FS mtime 해상도가 거친 스토리지(FAT, 일부 SMB는 1~2초)에서는 리스 판정과 메시지 순서도 그만큼
> 거칠어진다. 리스는 해상도보다 충분히 길게 잡는다.

## GC (크래시 잔재 정리)

크래시가 나면 다음 임시 파일이 남을 수 있다. 큐 동작에는 영향이 없지만 디스크를 조금씩 점유한다.

| 위치 | 잔재 | 생기는 때 |
|---|---|---|
| `tmp/` | 모든 파일 | 발행 중 크래시 |
| `control/` | `.now-*` | FS 시각 측정 중 크래시 |
| `control/` | `leader-*.tmp` | `leader.info` 교체 중 크래시 |
| `control/` | `election.lock.stale-*` | stale 락 회수 뒤 남은 옛 락 |

`fq_gc`가 이 중 임계 나이보다 오래된 것을 정리한다.

```c
/* 10분보다 오래된 크래시 잔재 정리 */
int removed = fq_gc(q, 10 * 60 * 1000);
```

활성 리더의 유지보수 주기(예: 수 분마다)에 한 번씩 호출하면 충분하다. 진행 중인 발행을 건드리지
않도록 임계 나이는 넉넉히(최대 발행·하트비트 소요시간보다 길게) 잡는다.

## 디스크가 가득 찼을 때

- `fq_publish`는 `FQ_ENOSPC`를 돌려준다. 실패한 임시 파일은 그 자리에서 지워지므로 실패가 남은 공간을
  더 갉아먹지 않는다.
- 소비는 계속된다: claim·ack·nack은 rename/unlink라 공간이 필요 없고, ack가 오히려 공간을 비운다.
  리더의 하트비트(leader.info 쓰기)가 실패해도 리스가 유효한 동안 claim을 계속하며, 끝내 갱신하지
  못하면 리스 자체 만료로 내려놓는다.
- `fq_gc`는 FS 시각을 재려고 파일을 만들 수 없으면 추정 FS 시각으로 대신해 정리를 계속한다.

## 긴 메시지 처리

메시지 하나의 처리가 리스(`FQ_LEASE_MS`)보다 길어질 수 있다면 처리 도중 리스를 연장해야 한다.
그렇지 않으면 `fq_consume`이 리스 자체 만료를 감지해 리더십을 내려놓고 다시 얻으며(token +1),
그 사이 다른 노드가 인수할 수도 있다.

```c
while (more_work(m)) {
    do_chunk(m);
    if (fq_heartbeat(q) == FQ_ELOCKED) {   /* 리더십을 잃음 → 새 리더가 회수해 재처리 */
        fq_msg_free(m);                    /* ack하지 말고 버린다 */
        break;
    }
}
```

## DLQ (dead-letter queue)

`dead/` 디렉터리에는 재시도 한도를 초과한 메시지가 모인다. 운영에서는:

- `dead/`의 파일 수를 모니터링하라. 쌓인다면 특정 메시지가 반복적으로 소비자를 실패시키고 있다는
  신호다(poison 메시지, 처리 로직 버그).
- 원인을 고친 뒤 `dead/`의 파일을 `incoming/`으로 옮기면 재처리할 수 있다. 이때 끝의 `.a<N>`
  접미사를 **떼고** 옮긴다(예: `…-x.msg.a4` → `…-x.msg`). 그대로 옮기면 attempt가 한도 직전이라 한 번만
  더 실패해도 곧바로 `dead/`로 돌아간다. 앞쪽 시각은 그대로라 큐의 맨 앞에서 처리된다.
- 영구 폐기 대상이면 그대로 삭제한다.

## 모니터링 포인트

| 관찰 대상 | 정상 | 이상 신호 |
|---|---|---|
| `incoming/` 적체 | 처리 속도가 따라감 | 계속 증가 → 소비자 처리량 부족/리더 부재 |
| `inflight/` 지속 잔존 | claim 직후 잠깐 | 오래 남음 → 현재 리더가 처리 중 멈춤(내 token은 회수 대상 아님) 또는 리더 부재. 옛 token 것은 다음 하트비트에 회수됨 |
| `dead/` 증가 | 0 또는 드묾 | 증가 → poison 메시지 |
| 활성 리더 수 | 항상 1 | 0(아무도 인수 안 함) 또는 2+(리스/스토리지 문제) |
